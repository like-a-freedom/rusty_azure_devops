# Migration plan: switch to `azure_devops_rust_api` as the single ADO backend (breaking change) ⚠️

**Goal:** Replace and remove the old `ReqwestAzureClient` implementation entirely and make `azure_devops_rust_api` the single, canonical way to interact with Azure DevOps across the repo. This is a one-way, breaking migration with no fallback to the old Reqwest implementation.

---

## Summary of findings (from docs)
- `azure_devops_rust_api` is an autogenerated SDK (v0.32.0) covering Work Item Tracking (`wit`), Projects (`core::projects`), WIQL, comments, etc. (docs: https://docs.rs/azure_devops_rust_api). ✅
- The SDK supports PAT auth via `Credential::from_pat` and exposes typed models such as `JsonPatchOperation`, `WorkItem`, and `Comment` which should become the canonical types for our code and schemas. ✅

---

## Migration plan (definitive, breaking)

IMPORTANT: This migration removes the old Reqwest-based implementation and makes the SDK the only supported backend. All changes are breaking by design and should be committed in an isolated, high-quality PR with tests and CI updates.

1. Make `with-ado` the canonical feature and **include it in `default`**, so the SDK is used by default in builds. Status: **done** ✅
- NOTE: The `with-ado` feature flag has been removed and `azure_devops_rust_api` is now a required dependency (SDK is always enabled).
2. Remove the old `ReqwestAzureClient` implementation and all its tests and helper code. Status: **done** ✅ (all call sites and tests migrated to `AutogenAzureClient`; legacy implementation replaced with a deprecation stub)
3. Implement the `AzureDevOpsClient` fully on top of `azure_devops_rust_api` (work item, queries, comments, projects, etc.), using SDK types where possible. Status: **done** ✅ (core operations implemented and covered by tests: list/create/get/update work items, comments, wiql, retry behavior)
4. Migrate **all schema generation and validation** to derive from or map to the SDK types and contracts. Prefer using SDK types directly for serialization/validation where feasible; when SDK types lack schema derives, add small wrapper types that derive `schemars`/`serde` and map to SDK types. Status: **done** ✅ (schema generator updated and `docs/schemas/` refreshed to match generated output)
5. Replace any custom, hand-rolled DTOs (for work items, comments, relations, etc.) with SDK types or stable wrapper types, and update API surface to use those types. Status: **planned**
6. Implement robust error mapping: translate SDK errors into our public error types or return SDK errors directly with clear conversion where it improves clarity. Status: **planned**
7. Add comprehensive integration tests (wiremock or recorded fixtures) to validate behavior and ensure parity between old behavior and new implementation. Status: **planned**
8. Update CI to run tests and linters with the new default behavior; document necessary environment variables (PAT, organization, project). Status: **planned**
9. Update documentation (README, AGENTS.md, docs) to state that `azure_devops_rust_api` is the only supported ADO backend and to show schema generation steps using SDK types. Status: **done** ✅ (README and docs updated; generator steps documented)
10. Tag a major version and include migration notes in CHANGELOG noting breaking nature. Status: **planned**

---

## Notes / Rationale
- The SDK provides first-class typed models and removes a large surface area of hand-written HTTP/serialization code. Moving schemas to SDK types improves correctness and reduces duplication. We will prefer SDK types directly where they satisfy our needs and add thin wrappers with `schemars::JsonSchema` when needed for schema generation.
